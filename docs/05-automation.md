# Автоматизация — Desktop QA Sandbox

## Идея

Проверки должны не просто «проходить», а **воспроизводить конкретные дефекты**. Поэтому для каждого дефекта
задан ожидаемый корректный результат; если приложение вдруг начнёт вести себя правильно, прогон покажет
`Fail` — сигнал, что стенд изменился и документацию пора обновить.

## Два режима

| Режим | Команда | Что делает | Где применим |
|-------|---------|------------|--------------|
| UI | `DesktopSandbox.UiChecks.exe <path-to-app>` | Запускает приложение, работает через UI Automation | Локально, интерактивный рабочий стол |
| Logic | `... --logic` | Проверяет `Rules` напрямую, без UI | CI, headless |

## Что проверяет UI-режим

| Блок | Проверки |
|------|----------|
| Registration | Валидные данные, e-mail без TLD, возраст 0/−5/`abc`, несовпадение паролей, короткий пароль, текст успеха |
| Orders | Начальный итог, однократная и повторная скидка, удаление без подтверждения, итог после удаления, сортировка Amount, поиск в другом регистре, точный регистр |
| Notes | Сохранение 300 символов (файл на диске), очистка без подтверждения |
| Окно | Закрытие с несохранённой заметкой |

## Как это устроено

1. `Process.Start` запускает `DesktopSandbox.exe`.
2. `AutomationElement.FromHandle(MainWindowHandle)` даёт корень дерева.
3. Элементы ищутся по `AutomationId` (`FirstNameBox`, `SaveRegistrationButton`, `OrdersGrid`, …).
4. Ввод — `ValuePattern.SetValue`, нажатия — `InvokePattern.Invoke`, таблица — `TablePattern`/`DataItem`.
5. Между действиями — короткие паузы; для нестабильных состояний предусмотрены повторные попытки
   и fallback (подсчёт строк по ячейкам, если `TablePattern` временно недоступен).
6. Результат печатается Markdown-таблицей: `ID | проверка | ожидание | факт | вердикт`.

## Формат вывода

```
| D-05 | Total is recalculated after deletion | Deleting Alpha Corp (100.00) gives 337.44 | 437,44 | Defect |
```

Итог:

```
- PASS: 3
- DEFECT reproduced: 15
- FAIL: 0
```

`DEFECT reproduced` — ожидаемый дефект подтверждён (это успех прогона).
`FAIL` — поведение отличается от задокументированного, требует разбора.

## Ограничения

- UI Automation видит только стандартные контролы; кастомные пришлось бы дополнять `AccessibleObject`.
- Прогон чувствителен к блокировке экрана/сессии: нужен активный пользовательский сеанс.
- Скриншоты в UI-режиме не делаются (это отдельный PowerShell-скрипт).
- Тест не проверяет вёрстку и пиксели — только поведение и данные.

## CI

В репозитории есть workflow `.github/workflows/dotnet.yml`:

- `dotnet build` обоих проектов;
- `--logic` прогон;
- публикация логов как артефакта.

UI-прогон в CI не включён осознанно: GitHub-hosted Windows runner не даёт интерактивного рабочего стола
для UI Automation.
